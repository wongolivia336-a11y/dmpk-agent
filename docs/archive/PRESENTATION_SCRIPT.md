# 肿瘤报告智能体工作空间原型汇报讲稿

汇报对象：当前版本原型

汇报目的：说明这一版的交互设计思路、用户体验判断和关键取舍。

核心主轴：

> 这一版不是把 agent 的技术过程展示给用户看，而是把 agent 的能力翻译成医药报告使用者能理解、能判断、能控制的任务体验。

## 0. 开场

大家好，这一版我主要汇报的是肿瘤实验报告智能体工作空间的交互原型。

我这次没有把重点放在“展示 AI 有多复杂”，而是回到真实用户的任务：用户要上传方案和数据，确认系统校验出的风险，生成报告草稿，查看关键产物，并在必要时做判断和确认。

所以这一版的设计目标可以概括成三句话：

1. 用户不需要理解 agent 怎么 function calling，只需要知道 agent 做了什么。
2. 用户不需要被所有过程信息淹没，只需要看到当前和自己决策有关的信息。
3. agent 不是替用户做最终判断，而是把依据和产物组织好，让用户仍然拥有选择权和主体性。

## 1. 整体信息架构

这一版的框架分成左侧 sidebar、中间对话流和右侧预览 panel。

左侧 sidebar 是三级关系：

- 一个 workspace 下可以有多个 project。
- 一个 project 下可以有多个 chat 对话。
- 每个 chat 对应一次具体报告任务或一次任务上下文。

这样设计的原因是，这类报告生成任务不应该只是一次性聊天。真实工作里，一个工作空间可能会承载多个项目，一个项目里又可能围绕不同报告、不同数据版本、不同沟通轮次产生多个对话。

所以左侧不是简单的历史记录，而是一个轻量的项目管理结构。它帮助用户知道：我现在在哪个 workspace、哪个项目、哪一次报告任务里。

这一点对 B 端工作台比较重要，因为用户不是来体验一个 AI demo，而是要在持续的项目上下文里完成工作。

## 2. 首屏上传：让任务入口足够明确

中间区域最开始是一个明显的上传面板。

这里我刻意用了一个比较显眼的拖拽框，提示用户可以把符合要求的文件拖进来，也可以主动选择文件。

这个任务的起点不是“和 AI 闲聊”，而是上传实验方案和实验数据。所以我希望首屏第一眼就告诉用户：

- 这里需要方案 DOCX。
- 这里需要数据 XLSX。
- 文件满足要求之后，才能进入后面的校验和生成。

上传成功且文件满足要求之后，我设计了一个绿色渐变光的轻提示。它不是强弹窗，因为不希望打断用户，但它要给用户一个明确反馈：文件已经就绪，可以继续。

这一段的设计判断是：上传不是普通附件功能，而是任务启动条件。因此它必须足够显眼、足够可验证。

## 3. 从 Chain of Thought 转译为 Agent 动作链

接下来进入 validation。

传统 agent 产品里经常会展示 chain of thought、tool use、function calling 之类的信息。这个逻辑在 coding 工具里可能成立，因为程序员关心 agent 调了什么工具、做了什么推理。

但这个项目面向的是医药行业用户，比如 SD、SD 助理。他们不一定关心 agent 背后怎么调用工具，也不应该被这些技术过程干扰。

所以我没有直接展示技术意义上的 chain of thought，而是把它转译成了 agent 动作链。

这里我想表达的不是“AI 在想什么”，而是：

- agent 做了什么？
- 依据是什么？
- 当前进展到哪一步？
- 用户接下来需要做什么？
- 最后产出了什么？

也可以把它理解成 chain of activity 或 chain of motion。它不是暴露模型思维，而是把 agent 的活动过程转成用户能理解的业务动作。

这背后的设计原则是：对医药报告用户来说，透明度不是展示技术过程，而是展示业务依据和责任边界。

## 4. 渐进式披露：默认减负，但保留可追溯

中间的对话流采用渐进式披露机制。

在任务进行中，用户默认看到的是当前阶段的核心进展和下一步动作。比如校验时看到校验动作，生成时看到生成动作，审核时看到专家建议处理。

当一个阶段结束后，这个动作链会自动折叠，但仍然保留展开入口。

这样设计是因为报告生成任务里信息量很大：文件、校验、warning、生成过程、专家建议、交付包、证据材料都可能同时存在。如果全部展开，用户会被信息淹没。

所以我把信息分成两层：

- 默认层：只显示当前决策需要的信息。
- 追溯层：用户需要查看依据、过程、细节时再展开。

这也是这一版的核心体验策略：不是隐藏信息，而是让信息在合适的时候出现。

## 5. Warning 确认：用户是判断主体

validation 结束后，如果发现 warning，系统不会直接进入 generation。

我把 warning 的确认区域放在输入 tab 上方，是因为这一步不是普通系统提示，而是用户必须做出的业务判断。

用户可以逐一确认 warning，也可以全部接受后继续生成。

如果用户不接受 warning，这个流程就不应该继续 generation。因为不接受 warning 意味着当前文件或数据条件不适合继续生成报告。因此我保留了“返回替换文件”的入口，让用户可以重新上传更合适的文件。

这里我想强调的是：agent 不是替用户承担责任。agent 可以提示风险、解释依据、组织材料，但是否接受风险、是否继续推进，仍然由用户判断。

所以 warning 这一步的设计重点不是“让用户快点点过去”，而是让用户明确知道：

- 当前有什么风险。
- 接受风险之后会发生什么。
- 不接受风险时可以怎么回退。

## 6. Generation：让产物成为主角

warning 确认后，系统进入 generation。

这一阶段仍然保留 agent 动作链，但它不抢占主视线。用户主要关心的是报告是否生成、生成了什么、还能查看哪些材料。

所以生成完成后，我让 agent 输出一段简短说明，同时把关键产物放出来，比如 Word 报告和交付包。

这里的设计判断是：到了 generation 之后，主角应该从过程变成产物。

用户不需要一直看 agent 做了多少内部动作，而是要快速知道：

- 报告是否已经生成。
- 交付包是否已经形成。
- 哪些内容还需要后续确认。

这也和前面的原则一致：过程信息可以追溯，但不要压过用户真正关心的结果。

## 7. 右侧 Panel：证据和预览不打断主线

关键产物和证据材料可以通过 hover 或点击在右侧 panel 中预览。

右侧 panel 既可以临时出现，也可以 pin 固定。这样用户可以一边看中间的任务流，一边对照右侧的报告、交付包或证据材料。

我这样设计是为了避免两种问题：

第一，不把所有材料都塞进对话流。否则中间区域会变成很长的材料堆叠。

第二，也不把证据材料藏得太深。因为医药报告场景需要可信、可追溯，用户必须能看到依据。

所以右侧 panel 的角色是“静默展示和辅助核对”，不是抢主流程。

它服务的是渐进式披露：需要的时候出现，不需要的时候让主任务保持干净。

## 8. 专家检查与用户主体性

报告生成后，原型进入专家检查和建议确认。

这里我想表达的是，agent 的 agency 和用户主体性要同时存在。

agent 有 agency，体现在它能主动完成校验、生成、整理证据、提出专家建议。

但用户仍然是主体，体现在关键节点都需要用户做选择和确认：

- 是否接受 warning。
- 是否继续生成。
- 是否确认专家建议。
- 是否查看和核对交付材料。

这不是一个“AI 自动替你完成一切”的体验，而是一个“AI 把复杂材料整理到可判断状态，用户做最终业务判断”的体验。

这对医药行业尤其重要，因为报告内容有责任边界，系统不能把最终科学结论和质量责任全部包装成 AI 自动完成。

## 9. 这版的设计关键词

如果总结这一版，我会用四个关键词：

第一，任务化。

这个界面不是聊天玩具，而是围绕报告任务展开。上传、校验、确认、生成、审核、预览都服务于一个任务闭环。

第二，业务透明。

我没有展示底层 tool use，而是展示 agent 对业务用户有意义的动作、依据和产物。

第三，渐进式披露。

默认只给用户当前需要的信息，过程、证据、技术细节都可以展开或在右侧 panel 查看。

第四，用户主体性。

agent 可以主动推进任务，但关键风险和确认动作仍然交给用户判断。

## 10. 可能会被问到的问题

### 问题 1：为什么不直接展示 agent 的完整思考过程？

因为这个产品的用户不是程序员。完整技术过程对他们不是透明，而是噪音。

我这里把透明度重新定义为：用户知道系统做了什么、依据是什么、自己需要判断什么、产物是什么。这比展示 function calling 更符合医药报告场景。

### 问题 2：为什么 warning 不接受时不能继续生成？

因为 warning 是生成前的风险边界。如果用户不接受，就说明当前材料或条件不适合继续生成。继续生成会让责任边界变模糊。

所以我保留了返回替换文件的路径，而不是让用户忽略 warning 继续往下走。

### 问题 3：为什么右侧 panel 要能 pin？

因为用户在审核报告或确认证据时，经常需要对照查看。临时 hover 适合快速看一眼，pin 适合持续核对。

这样主流程不被打断，但证据材料也不会藏得太深。

### 问题 4：这版和普通聊天机器人有什么区别？

普通聊天机器人以输入输出为中心，这一版以任务路径为中心。

聊天只是交互方式之一，真正的结构是：文件准备、校验、风险确认、报告生成、专家检查、交付预览。

### 问题 5：这个原型如何体现可信感？

可信感来自三个方面：

- 文件要求明确，用户知道输入边界。
- 每个阶段有动作链和依据，不是黑箱生成。
- 关键风险需要用户确认，最终责任边界没有被 AI 模糊掉。

## 11. 收尾

最后总结一下，这一版我的设计重点不是让界面看起来更像 AI，而是让 AI 能被真实业务用户使用。

我把 agent 的技术过程转译成业务动作链，把复杂信息放进渐进式披露结构里，同时保留用户在风险确认和报告审核中的主体性。

所以这版原型想验证的是：在医药报告生成场景里，agent 工作空间能不能既体现自动化能力，又不剥夺用户的判断权；既能提供足够依据，又不造成信息过载。

这就是我这一版的主要设计思路。

## 12. 口播压缩版

如果汇报时间很短，可以直接讲这一版：

这版我主要想解决的是：医药报告用户不需要看 agent 的底层 chain of thought，也不关心 function calling 或 tool use。他们真正关心的是 agent 做了什么、依据是什么、我需要判断什么、最后产出了什么。

所以我把传统的 chain of thought 转译成了 agent 动作链。它展示的是业务动作，不是技术推理。

整体结构上，左侧 sidebar 是 workspace、project、chat 的三级关系；中间是任务对话流；右侧是可 hover 或 pin 的预览 panel。

首屏先用显眼的上传面板让用户拖入方案 DOCX 和数据 XLSX。文件满足要求后给出绿色轻反馈，然后进入 validation。

validation 结束后，如果有 warning，用户必须逐一确认或全部接受才能进入 generation。如果不接受，就返回替换文件。这样能保证用户仍然是风险判断的主体，而不是被 agent 自动带着往下走。

生成完成后，动作链自动折叠，报告和交付包成为主角。过程信息仍然可以展开，关键产物和证据可以在右侧 panel 预览。

所以这一版的核心是渐进式披露：默认只展示用户当前关注的信息，需要追溯时再展开。最终目标是让 agent 既有主动性，又不剥夺用户在医药报告场景里的判断权和责任边界。
