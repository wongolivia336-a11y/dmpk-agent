# 任务路径审判式 UX 走查

版本对象：`http://127.0.0.1:4196/`

走查目的：给设计者自己使用，只找交互和用户体验问题，不直接修改原型。

本轮主力角色：

- UX 找茬专家：从真实用户任务、理解成本、状态反馈、阻断点出发挑问题。
- 竞品调研员：不列产品名凑数，只把问题翻译成可迁移的交互模式。
- 可交付验收员：负责打回空泛建议，判断问题是否影响客户可体验。

本轮证据：

- 当前原型首屏截图：`G:\实习\澎立肿瘤报告项目\prototype-agent-workbench\output\playwright\ux-review-home.png`
- 当前任务状态流：`empty -> uploaded -> validating -> warning -> generating -> review -> exported`
- 当前核心任务：上传方案 DOCX / 数据 XLSX，校验，确认 warning，生成报告，专家建议确认，查看交付包。

## 总结结论

当前版本已经从“说明型 demo”往“真实工作台”迈了一大步，尤其是上传文件要求、底部输入栏上传入口、warning 确认、产物预览这些关键节点已经成型。

但从任务路径看，最大风险不是“功能不够”，而是“用户在每一步到底是在做业务决策，还是在看系统过程”仍有混杂。当前界面把 agent 过程、业务证据、专家建议、交付物预览都放进同一条对话流里，真实用户可能会完成任务，但不一定能快速判断：我现在该确认什么、确认后承担什么、下一步会发生什么。

所以这轮不建议继续堆新功能。应该先用任务路径审判法，把每一步的用户动作、系统反馈、风险边界和可借鉴模式对齐。

## 任务路径 1：进入任务与上传文件

当前状态：

- 空状态提供“拖入方案和数据，开始一份报告任务”。
- 明确要求 1 个 DOCX 和 1 个以上 XLSX。
- 上传后有文件准备面板，能显示缺什么文件。
- 底部 composer 已补充上传 icon，支持对话中继续补充文件。

UX 找茬专家：

- P1：首屏上传入口的“报告任务”概念比“上传文件”更高级，但也更抽象。首次用户可能先理解任务是什么，而不是立刻知道这里可以点击或拖拽文件。
- P1：空状态和底部输入栏都有上传入口，这是好事，但两个入口的关系还没有被解释清楚。用户可能不确定底部上传是补充材料，还是重新开始任务。
- P2：上传入口使用品牌图形作为视觉中心，可信感有了，但可操作感略弱。真实工作台里，文件投放区通常更像 drop zone，而不是一个品牌卡片。

竞品调研员反驳与补充：

- 不建议改成夸张的大上传框。这个产品不是网盘，也不是单纯文件转换器，上传只是报告任务的开始。
- 可迁移模式应该参考“任务创建面板 + 文件要求清单”，而不是“纯上传组件”。
- 更好的模式是：首屏保留任务语义，但让可操作区域更明确，比如“拖入或选择文件”作为主动作，“需要 DOCX/XLSX”作为校验条件。

可执行建议：

- 保留当前任务型上传方向。
- 把首屏主动作语义从“报告任务”稍微压低，强化“选择文件 / 拖入文件”。
- 底部上传 icon 的语义应定位为“补充文件”，不要让它像重新开始任务。

验收方式：

- 新用户 5 秒内能说出：这里要先上传 DOCX 和 XLSX。
- 上传一个文件后，用户能知道还缺什么，而不是只知道“等待补齐”。

## 任务路径 2：文件满足后开始校验

当前状态：

- 文件满足要求后，主按钮“开始校验”可用。
- 文件未满足时按钮不可用。
- 文件准备面板能显示“文件已满足要求 / 等待补齐文件”。

UX 找茬专家：

- P1：按钮不可用时，原因主要分散在文件槽位和状态文字里。用户能看懂，但要扫两处。
- P1：“开始校验”是系统动作，不是用户收益。用户可能知道会校验，但不知道校验会回答什么问题。
- P2：文件通过条件是 DOCX + XLSX，但如果上传了其他文件类型，当前体验需要明确它被忽略、归为 other，还是阻断。

竞品调研员反驳与补充：

- 数据质量平台常见模式不是只写“开始校验”，而是告诉用户校验范围：文件识别、统计上下文、QA 初筛。
- 但不要把全部校验步骤提前展开，否则又回到流程说明页。
- 可迁移模式是“主按钮 + 一句结果预期”：开始校验，检查文件完整性与生成风险。

可执行建议：

- 主按钮旁或下方增加短提示：校验会检查文件完整性、统计上下文和报告生成风险。
- 不要提前暴露完整技术流程。
- 文件类型错误、重复上传、缺失文件应有单独提示，不要全部归到“等待补齐”。

验收方式：

- 用户点击“开始校验”前知道校验不是最终生成，而是进入风险判断。

## 任务路径 3：校验中

当前状态：

- 进入 validating 后，对话流显示“校验过程”ThinkingCard。
- 支持展开过程、查看技术细节和右侧详情。

UX 找茬专家：

- P1：校验中展示过程是可信的，但过程信息有挤占主任务的风险。用户最关心的是“还要等多久 / 有没有问题 / 下一步是什么”。
- P1：elapsed 是固定展示，可能让原型显得真实，但如果没有进度预期，会更像装饰性过程。
- P2：技术详情入口存在价值，但默认应该服务技术评审，而不是普通报告使用人。

竞品调研员反驳与补充：

- AI 工作台确实需要过程透明，否则用户不信任结果。
- 但医疗/实验报告场景的透明不是“展示 agent 在干什么”，而是“展示依据、边界和责任”。
- 可迁移模式：默认展示业务级进度，技术细节折叠在 secondary layer。

可执行建议：

- 校验中默认显示 3 个业务级进度：识别文件、检查数据、生成风险摘要。
- 技术 trace、agent step、内部过程继续折叠，不作为主阅读内容。
- 校验中应提前告知下一步会进入 warning 确认或直接生成。

验收方式：

- 用户不展开任何详情，也能知道系统正在做什么、下一步可能是什么。

## 任务路径 4：校验完成与 warning 确认

当前状态：

- 校验完成后出现 warning 说明。
- 底部有 warning 决策面板。
- 用户可逐条“接受此风险”，也可“全部接受并生成”。
- 有“返回替换文件”。
- 文案说明“确认 warning 不等于确认最终科学结论”。

UX 找茬专家：

- P0/P1 边界问题：这是当前最重要的业务决策点，但用户可能仍然把它当成普通确认按钮。接受 warning 不是普通继续，而是风险授权。
- P1：“全部接受并生成”效率高，但风险边界强。真实产品里，批量接受通常需要更明确的二次确认或摘要。
- P1：warning 的证据入口存在，但用户不一定知道必须先看证据还是可以直接接受。
- P2：“warning”一词偏工程/系统，客户或业务用户可能更理解“需确认的风险项”。

竞品调研员反驳与补充：

- 审核流产品里，风险确认一般会把“风险项、影响范围、确认后动作”放在同一行，而不是只给一个接受按钮。
- 医疗/实验报告场景不适合轻量化到“全部同意”。批量接受可以保留，但要让它看起来像负责的业务动作。
- 可迁移模式：风险项列表 + 证据预览 + 确认声明。用户确认的是“允许进入生成”，不是“科学结论正确”。

可执行建议：

- 把 warning 文案逐步替换成“需确认的风险项”。
- “全部接受并生成”前应显示摘要：3 条风险将被记录为用户已确认，进入报告草稿生成。
- 每条风险行应更直接地呈现“影响范围”，减少用户必须打开详情的压力。

验收方式：

- 用户能清楚说出：我接受的是进入生成的风险，不是确认最终结论。

## 任务路径 5：报告生成

当前状态：

- 进入 generating 后显示“生成过程”ThinkingCard。
- 生成完成后出现报告草稿和交付包。
- 主对话保留 Word 报告和交付包，其他产物在右侧面板或弹窗中查看。

UX 找茬专家：

- P1：生成过程和校验过程的视觉/交互结构类似，用户可能感觉只是系统继续跑，而不是已经进入新的业务阶段。
- P1：报告生成后出现产物，但“草稿 / 可下载 / 需审核后放行”的关系仍要更强。
- P2：Word 报告文件名很长，真实可信，但列表扫描负担重。

竞品调研员反驳与补充：

- 文档自动化工具通常会区分“草稿生成完成”和“交付包可放行”。这两个状态不该被一个成功态混在一起。
- 可迁移模式：产物卡片分层。核心产物可见，过程产物折叠，放行条件单独展示。

可执行建议：

- 报告生成完成态应明确标注“草稿已生成，等待专家建议确认”。
- 产物卡片上区分“可预览”“待放行后下载”“过程材料”。
- 长文件名可保留，但卡片标题应该先表达业务对象：Word 报告、交付包。

验收方式：

- 用户能分清：现在已经生成草稿，但还不能等同最终交付。

## 任务路径 6：专家检查与建议确认

当前状态：

- 生成后自动进入专家检查。
- 显示专家检查过程、审核问题列表、确认此模块、全部确认、补充问询。
- 确认全部建议后进入 exported。

UX 找茬专家：

- P1：专家检查很有产品差异化，但“专家小队”容易让用户觉得像 AI 自说自话。真实审核流需要更明确的角色责任和处理动作。
- P1：“确认此模块”这个按钮语义偏弱。用户到底是在确认建议已读、确认处理完成，还是确认接受建议？
- P1：“补充问询”是好入口，但它在任务路径里的地位不够明确。它是问 AI、补材料，还是请求人工复核？

竞品调研员反驳与补充：

- 审批流产品的关键不是“专家是谁”，而是“每条建议需要什么处理结果”。
- 可迁移模式：每条审核建议有状态和处置动作：接受建议、补充证据、标记无需处理。
- AI 工作台可以保留专家角色，但不要让角色成为主角，主角应该是待处理建议。

可执行建议：

- 把“专家小队已完成检查”弱化为“发现 3 条需处理建议”。
- “确认此模块”改为更具体的动作，例如“确认已处理”或“接受此建议”。
- “补充问询”应说明输出是什么：补充解释、补证据、还是返回修改材料。

验收方式：

- 用户能逐条判断建议该如何处置，而不是只点击确认通过。

## 任务路径 7：查看报告与交付包

当前状态：

- 产物预览弹窗包含 Word 报告、交付包、Prism 源文件、Figure 图片、QC 报告、业务证据摘要、专家建议文档。
- 交付包预览说明不会暴露临时 URL 或内部 bucket 路径。
- Word 预览说明完整下载前仍需完成审核和权限校验。

UX 找茬专家：

- P1：产物预览内容很完整，但对业务用户来说入口层级可能偏深。主路径里只看到两张产物卡，更多材料藏在弹窗目录里。
- P1：产物分类合理，但“哪些是客户交付，哪些是内部质量材料，哪些是技术源文件”需要更明确。
- P2：预览弹窗更像完整材料库，可能抢走主任务焦点。

竞品调研员反驳与补充：

- 报告生成工具常用“交付包清单”模式：核心交付、源文件、质量材料、证据摘要分组展示。
- 这个原型已经有分组雏形，但应该把“交付对象”标出来。
- 可迁移模式：交付物矩阵，按使用者分为客户可见、项目组可见、技术追溯。

可执行建议：

- 产物预览目录中增加使用者语义：客户交付、内部 QA、技术追溯。
- 主界面的产物卡保留 2 个核心，不要把所有过程产物前置。
- 弹窗标题可从“产物预览”进一步变成“交付物与证据材料”。

验收方式：

- 用户能快速判断哪些文件要交付客户，哪些只是内部检查材料。

## 任务路径 8：最终导出 / exported

当前状态：

- 全部专家建议确认后进入 exported。
- 会出现专家建议文档。
- 文案强调最终是否通过仍由 SD / QA / 统计角色签核决定。

UX 找茬专家：

- P1：最终状态的任务完成感还不够明确。用户完成确认后，应该得到一个清晰的“现在可以做什么”。
- P1：如果最终导出仍受权限和门禁限制，用户需要知道下一步是下载、提交放行、还是等待签核。
- P2：exported 这个状态在界面上不应被用户感知为技术状态，而应是业务状态。

竞品调研员反驳与补充：

- 审核流的完成态一般会给出“下一步动作组”：下载草稿、提交 QA、查看确认记录、复制交付清单。
- 可迁移模式：完成态行动面板，而不是只展示成功消息。

可执行建议：

- 完成态应明确三个动作：查看报告、查看确认记录、进入最终放行/下载。
- 如果下载未真正接入，应标注“原型预览”或“等待后端接入”，但不能暴露内部技术过程。

验收方式：

- 用户完成全部确认后，不会停在页面上问“然后呢？”

## 互相批驳后的本轮 P0/P1 清单

### P0 候选

当前没有“完全无法完成任务”的硬阻断。上传、校验、warning、生成、审核、预览路径都已经可以串起来。

但有一个接近 P0 的风险：

- 风险确认语义不够重。用户可能把“接受 warning / 全部接受并生成”理解成普通继续，而不是业务风险授权。

### P1

1. 每个阶段的下一步动作需要更明确，尤其是校验完成、生成完成、审核完成。
2. warning 应从系统词转成业务词：“需确认的风险项”。
3. 专家建议确认动作语义需要收紧，避免“确认此模块”过于模糊。
4. 产物预览需要区分客户交付、内部 QA、技术追溯。
5. 校验/生成过程透明度应该更偏业务依据，少一点过程展示。
6. 底部上传入口应明确是“补充文件”，避免和首屏上传任务混淆。

### P2

1. 长文件名影响卡片扫描效率。
2. 空状态品牌视觉强于 drop zone 可操作感。
3. 预览弹窗内容丰富但略像材料库，容易分散主路径注意力。
4. “专家小队”等表达有差异化，但可能让严肃报告场景显得偏拟人。

## 建议采用的走查协作形式

以后每一轮都按这个格式跑，不直接让 agent 自由发挥：

1. 先定本轮任务路径：上传、校验、风险确认、生成、审核、导出，只选 1-2 段。
2. UX 找茬专家先输出问题，不允许给视觉风格建议。
3. 竞品调研员只回答“这个问题可迁移什么模式”，不允许只列产品名。
4. 两者互相批驳一次：UX 负责问“这个模式解决我的问题了吗”，竞品负责问“这个问题有没有更成熟的行业模式”。
5. 可交付验收员最后只保留 P0/P1，打回空泛、无法落地、只说好看的建议。
6. 产物写成 markdown，必要时再转 Figma 批注。

## 下一轮推荐拷问问题

下一轮不要全页面再走一遍，建议只挑一段：

1. warning 风险确认是否应该升级为更正式的“风险授权面板”？
2. 专家建议确认到底是“已读确认”“接受建议”还是“处理完成”？
3. 生成后的交付物应该按文件类型分，还是按使用者分？
4. 技术过程透明度应该默认展示到什么程度，才既可信又不吓人？
